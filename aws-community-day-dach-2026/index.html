EU region ≠ sovereign partition

Decision framework

Three buckets — workload-specific, not org-wide

First question: what sovereignty requirement do you have? — not which vendor shouts loudest.

Bucket 1

eu-central-1 is enough

EU residency suffices · no partition mandate · full AWS catalog

Bucket 2

ESC for defined workloads

Contract/political sovereign partition · hybrid with eu-central-1

Bucket 3: ESC + on-prem / Hetzner / national cloud — deliberate full sovereign stack

Bucket 1 — most of you land here

  • EU data residency meets contractual needs
  • No requirement for isolated partition or EU-only operations
  • You want Lambda, Bedrock, full service breadth without split
  • That's OK — don't over-engineer sovereignty

Bucket 2 — phased ESC migration

  • Finance, health, federal IT, critical infrastructure
  • Hybrid: core on ESC, rest stays on eu-central-1
  • Path: readiness → landing zone → pilot → rollout

For builders

Partition & identity

  • Separate IAM identities — no 1:1 copy from standard accounts
  • ARN formats change · new landing zone / account layout
  • Billing and organizations are partition-scoped

DNS & networking

  • Route 53 zones and behavior — frequent migration pain point
  • Cross-partition references: plan explicitly or avoid
  • VPC endpoints, private DNS — verify per service in ESC

IaC / CDK / Terraform

  • Region: eusc-de-east-1
  • Partition: aws-eusc
  • Hardcoded eu-central-1 ARNs break silently or at deploy
  • CI/CD: separate credentials · often separate pipelines
  • Check service availability before design — not everything from Frankfurt is in ESC yet

At GA

Serverless stack — verify, don't assume

  • Lambda · API Gateway · EventBridge
  • S3 · DynamoDB · SQS · SNS
  • Step Functions · CloudWatch
  • Always check ESC service matrix
  • "In eu-central-1" ≠ "in ESC"
  • Bedrock / newer services — confirm GA status
Point to official ESC service list. Update slide before conference if GA set changed.

Live walkthrough

CDK stack migration — concrete steps

  1. Clone working stack from eu-central-1
  2. Set env.region → eusc-de-east-1
  3. Replace partition in ARNs · IAM paths · SSM parameters
  4. Route 53 hosted zones — recreate or import per ESC rules
  5. Deploy pilot · run integration tests · compare cost & latency

DACH context

Regulation driving sovereign cloud projects

  • NIS2 — critical entities, supply chain, incident reporting
  • DORA — financial sector ICT resilience
  • GDPR — data residency & processor obligations
  • EU AI Act — high-risk AI + data governance overlap

ESC is an architecture option for sovereignty requirements — not automatic compliance.

Honest take

CLOUD Act & third-country access

What ESC addresses

  • Physically isolated EU infrastructure
  • EU-resident operations — no global US ops path
  • European governance structure

What it doesn't replace

  • Contract review (subprocessors, support)
  • Data classification per workload
  • Political expectations vs technical reality

eu-central-1 hosts in EU but partition stays aws — that's the distinction lawyers ask about.

Who's on it

Public reference direction (not migration playbooks)

  • SCHUFA — credit data, EU-only ops narrative
  • ITZBund — federal IT commitment
  • EWE — energy / critical infrastructure
  • SAP — ERP on sovereign partition
  • UK Essen / Lausitz — health & research
  • Pattern: hybrid · workload-specific · not org-wide big bang

Gap: IAM layout, CDK paths, timelines — where readiness assessments start.

Hybrid

Sovereignty is not either/or

  • ESC for sovereignty-critical workloads
  • eu-central-1 for everything else
  • Or self-hosted EU (Hetzner, on-prem) for greenfield — different trade-off
  • Most enterprises: Bucket 2 hybrid, phased
